## 已证明的问题与修复

1. **本地状态写入缺少零进展判断与明确错误传播。** write_json_atomic 遇到持续零字节写入可能循环不退出；mkdir、mkstemp、write、fsync、close、replace 及父目录同步的 OSError 会直接逃逸。新增八条源码链路在原实现上为 7 FAIL / 1 PASS，其中正常部分写入原本通过。零进展测试在第二次调用时主动报错，避免真的卡死。
2. **关闭失败可能重复关闭相同描述符编号。** 当 close 已释放描述符但仍报告错误时，旧 finally 会再次关闭。修复为关闭前结束本函数对该编号的所有权。失败注入验证没有第二次 close。
3. **reset 后缺少未跟踪文件收尾检查。** 原实现只在 reset 前隔离未跟踪控制文件。定点让真实 reset 返回后留下未提交任务或冲突文件，两条源码链路均失败：前者可能被执行，后者可能被当成远端已存在而不再补发。现于最后一次 reset 后再隔离并保存未跟踪文件，修复后两条均通过。该试验证明边界缺口，不证明下述原始异常由 Git reset 本身造成。

写入无进展立即停止。替换前的已观测 I/O 错误返回 local_state_write_failed / indeterminate；确认替换后父目录同步失败返回 local_state_durability_unconfirmed / indeterminate。二者都不能被解释为整个任务未执行。清理限于本次临时文件，保留旧目标、已替换的完整目标及其他轮次的临时证据；清理错误不覆盖原始异常。尺寸与协议校验保持原约束。

## 首轮真实失败与调查限度

首候选的 23 条指定源码链路、编译、wheel 构建和安装通过，但安装态在 **49 checks / 147 commands** 时失败：第 146 条健康 Worker 返回 0，第 147 条 Controller 等待 LH9996 返回 3 / controller_wait_timeout。该轮报告保持 FAIL，没有改写为 PASS。

冻结现场中，Worker 与 Controller 的 HEAD 均为模拟删除冲突的提交，远端没有相应冲突记录；两个工作副本各有一份未跟踪冲突文件，字节与本地持久 marker 一致，outbox 为空。独立复制整个失败 fixture 并追踪实际 Git 操作后，恢复成功，远端出现对应 blob，CAS 未重执行；原现场未用于复跑。

**原始异常的产生时序和底层根因仍未确定。** 本轮补上有独立失败证据的 reset 后边界检查，并在最终安装态定点模拟残留文件。不能用补丁后的 PASS 倒推已经解释原故障。

第二次安装尝试在同一最终候选上完成 49 checks / 146 commands 后，因归档数量断言失败而保持 FAIL：观察到两份字节相同的冲突归档，以及额外的 results/.rsync-tmp/LH9995.json。后者字节与该轮原 Result 一致；仓库源码没有 rsync 调用。该观察支持检查运行环境中的文件干扰，但尚未证明文件由哪个进程创建。

随后保持代码、测试及断言不变，将 checkout、build/runtime venv 和整个安装 fixture 全部建在新的独立临时目录，运行期间不再并行读写工作区文件，再执行指定链路。该隔离重验的结果列于下表。两轮失败日志和归档均保存；不将隔离后通过当作根因已经确认。

| 注入位置 | 必须保留的事实 | 故障消失后的恢复 |
