# 多节点独立 Local Hand 与 NAS 成果存储：实现方案

状态：目标设计与实施拆分，尚未完成跨平台多节点实现或部署验收。

目标是让同一个 Local Hand 产品版本分别部署到多个独立执行节点，覆盖 Linux ARM64、Linux x86_64 和 Windows AMD64。每个实例只执行自己的任务，拥有独立身份、权限、工作区、进程和恢复记录；调用方可以连接其中一个，也可以分别向多个实例提交任务，使任务跨节点并行。NAS 是独立的成果存储／服务节点，不因被使用而成为 Local Hand 执行节点。

本方案扩展部署形态、平台适配和成果存储接入，不改变原有职责主线：**调用方提出获准任务 → 指定节点受控执行 → 调用方核对原任务的状态与证据，继续工作**。不增加中央任务调度器，不让一个 Local Hand 代理另一个执行。

## 1. 基线与已有能力

本方案依据以下准确源码基线；“已有”不等于所有目标平台和部署节点均已验证。

| 对象 | 源码基线 | 能力与限制 |
|---|---|---|
| Local Hand | `bdca03384795236addc53c9df9cb1976b746b7bc` | 已有常驻 MCP、受限作业、原任务状态／证据和本地成果归档路径；当前执行与 prepare 链仍有 Linux 及 x86_64 假设 |
| Artifact Ledger | `78d6c5b07d47898083a47ac85d67cc5966b3760b` | 已有成果／版本／内容 API，以及封存快照向 NAS 发布、核验、恢复；没有在线多客户端归档服务或多租户权限接口 |
| 设计范围 | 本文、目标图的 Mermaid／SVG／PNG | 产品方案，不代表服务、业务任务、数据库、依赖锁或部署配置已经变更 |

上述 Ledger 基线中已验证的 A2 是“本地成果库 → 封存快照 → NAS → 新本地库恢复”，不是多个客户端远程打开同一个成果数据库。参见 [Ledger 基线说明](https://github.com/kongbu0621/infra-artifact-ledger/blob/78d6c5b07d47898083a47ac85d67cc5966b3760b/README.md)。

核心包的平台验证不能替代完整 MCP 与作业后端的原生验收。每个部署都必须核实实际宿主、操作系统和执行域；不能把虚拟机内部能力当作宿主能力。

| 概念 | 负责什么 | 所在位置与边界 |
|---|---|---|
| 执行节点 | 准入、执行、查询、取消、收集结果 | 各自独立的 Local Hand；只能控制自己的执行域 |
| 节点执行与恢复记录 | 原任务身份、请求指纹、执行状态、退出证明、恢复关联与长期归档索引 | 各节点私有、可靠的本地存储；不是供多个执行节点共同写入的 NAS 数据库 |
| 有界待归档成果 | 封存证据、原归档请求、目标绑定、回执和重试状态 | 各节点私有暂存；有容量和保留规则，不是无限缓存 |
| 成果存储节点 | 保存成果身份／版本／内容，查询、核验、准确读回和备份 | 可绑定同一 NAS，也可分别绑定不同 NAS；不取得业务执行权 |

图中的节点 A、B、C 是三个合成示例，不限定部署数量，也不映射到实际设备。示例节点可以绑定同一存储节点，也可以绑定不同存储节点。**共用一台 NAS 不等于共用任务状态、凭据、写权限或同一个数据库。** 初版建议同一存储服务内按 producer 映射到独立的受保护成果库，降低跨节点越权和恢复耦合。

存储逻辑身份与物理位置分离：完整目标绑定为 `storage_id + store_id + producer + binding_revision + store_generation`。其中 storage 标识存储节点，store 标识该节点内具体成果库，binding 标识已批准的配置版本，generation 区分恢复／重建后的库世代。`storage_ref`／`store_ref` 是受保护配置中的引用；请求、响应和 outbox 必须核对解析出的完整身份。网址、IP、盘符和挂载点均不充当身份。

普通重启或凭据轮换不改变库世代；恢复前先停写、核验快照和原回执／幂等历史，显式批准恢复绑定后才开放。客户端不得自动接受服务端报出的新世代，世代数字本身也不证明历史完整。NAS 可以迁移位置，但既有任务的目标绑定不能随配置悄悄改变。

只抽象确有差异的边界：执行平台、执行身份、成果存储接入。不要把机器、NAS、任务进程强行实现成一个通用节点类，也不要为各部署维护分叉的工程副本。

## 3. 多连接与任务身份

### 3.1 调用方连接方式

每个部署使用可区分的连接标签，如合成示例 `Local Hand · Node A`、`Local Hand · Node B`。接口可以同名，但每次调用必须明确选择连接，并核对其返回身份；不能靠工具名称或模型记忆路由。

连接登记时固定预期 node／install；若绑定节点 A 的连接实际返回节点 B 身份，应拒绝，而不是照抄发现结果自动重绑定。合法更换安装由显式更新连接绑定处理，旧任务引用仍保留原来源。

OpenAI 文档允许自定义 MCP 应用与其他应用共同使用，但实际可选连接、工具权限与账户／工作区配置仍需实测。多连接不自动提供持续规划或无人值守调度；本方案只保证已接受任务由目标节点独立管理，持续推进下一步仍由调用方或另行授权的控制方决定。[官方接入说明](https://developers.openai.com/api/docs/guides/custom-mcp-server)

### 3.2 区分三层身份

1. **当前部署身份**：`node_id + install_uuid + deployment_epoch`，加实际执行域和部署能力描述。
2. **原任务身份**：原节点／安装身份、`operation_id`、提交主体和原请求指纹；与原始能力快照及证据封印关联。
3. **内部执行身份**：每次受控任务分配的 authority、ledger、manager 和进程／容器身份。它们不能替代稳定节点身份。

节点内使用 UUID 并不足以解决跨节点路由：两个节点即使出现相同 `operation_id`，查询、取消、证据读取也必须仍然互不影响。升级后同时报告当前服务部署与原任务来源，不能把旧任务“改籍”为当前部署。

进程重启不改变 node／install；普通升级按明确规则更新 epoch／版本，真正新安装产生新的 install UUID。稳定连接身份来自受保护 resident 配置，不能取自旧任务 policy 或每任务 authority。任务特定 profile／policy／registry 摘要在 prepare 中形成并绑定原任务；初始 capabilities 不伪造尚不存在的任务策略。

提交主体使用不可回收给其他身份的持久 `principal_id`。更换 issuer 或 subject 映射时，须核实同一主体的连续性；不能通过复用旧名字继承查询、取消或证据访问权。旧任务所有权不随当前登录配置改写；首版不提供向其他主体共享或转移任务权限的接口。

认证来源按 `(issuer, subject)` 识别；相同用户名、邮箱、`subject` 字符串或 OAuth `client_id` 都不能跨 issuer 证明同一主体。`client_id` 标识接入应用，不标识 ChatGPT 用户：现有单 client 配置可以映射多个 subject。两个 ChatGPT 账号需要隔离时分别登录两个本地主体，每个主体可获准多个项目；若都登录同一本地主体，则共享该主体的任务权限。本地管理入口及部署说明须明确这一区别，不从聊天账号名称推导主体。

### 3.3 具体接口改动

| 当前代码 | 拟修改点 | 必须保持的约束 |
|---|---|---|
| `tools/local_hand_jobs/contract.py`、`deployment.py` | 增加版本化节点控制封套；prepare、读取、查询、取消都绑定目标身份，能力发现返回稳定部署信息 | 保留 `lh-job-v1` 原字节、摘要和历史证据；旧客户端显式兼容或拒绝，不静默省略校验 |
| `tools/local_hand_mcp/resident.py`、`server.py`、`prepared.py` | 常驻能力发现保留原任务能力关联；所有入口核对当前目标与原任务来源 | 不能只在 submit 检查；错误节点在文件访问、prepare 和管理调用前拒绝 |
| `broker.py`、`state.py`、`evidence_client.py` 及客户端路由 | 原任务引用贯穿状态、取消、manifest、chunk、分页游标和证据缓存 | 缓存键至少含主体与完整任务／节点来源；不能只按 artifact ID 跨节点命中 |
| `tools/local_hand_connect/`、本地 CLI、受保护 manager 协议 | 端到端传递并校验目标封套和响应来源 | 本地或特权入口不能绕开网络入口的身份约束 |
| `tools/local_hand_mcp/auth.py` | 每个服务使用独立 resource audience、受控 issuer/JWKS 与主体映射 | 仅面向节点 A 的 token 不应可取消节点 B 的任务；NAS 凭据不能变为任务执行权 |
| `contract.py`、resident 与受保护 manager 的准备／提交／取消协议 | 版本化控制封套承载逻辑准备意图及整机队列，明确意图摘要与物理请求摘要的关联 | 旧 `lh-job-v1` 请求与摘要保持原义；旧客户端不能被静默当成已经授权新队列协议 |

复用既有原请求去重与恢复机制。版本化控制封套是路由／准入边界，不再发明第二套业务执行协议。查询原任务时，显式区分“当前服务可处理该查询”和“历史任务由旧部署接受”。

prepare 不是永久执行许可。准备后发生升级、项目撤权或能力配置变化时，首次 submit 必须重验并绑定当前节点、主体权限／撤销、项目及能力版本；受保护 manager 的首次启动也须核对同一有效准入，不能只在 MCP 层检查后继续沿旧 policy 放行。不兼容的准备明确拒绝。尚未正式提交、没有未决执行的准备可按显式流程重新准备并保留旧关联；新队列已经接受的意图不能按此规则原地改写，按第 3.4 节区分环境重绑定与新输入提交。已接受或结果未知的业务继续沿原身份核对，不因升级重提。旧任务读取兼容不等于旧准备仍可首次执行。

### 3.4 并行与恢复

2026-10-23 Owner 确定首版每台机器的并行上限先设为 **5 个任务，名额满时新提交自动排队**。这替代本节此前“每节点一个任务、不扩单节点并行”的范围；仍不提供跨节点选机、调度或代跑。所有账号、连接及项目共用这 5 个名额，不是每账号 5 个；一个主体可以获准使用多个项目，不固定为一账号一项目。5 是可配置的上限，不是任何负载下都已证明可以跑满的容量。

不同物理机器分别拥有自己的名额池和队列。同一 ChatGPT 账号分别取得各节点授权后，不受 Local Hand 跨机合计 5 个的限制；两机资源充足时可各执行 5 个，合计 10 个，各自第六项在原机器等待。A 机满额、取消或离线不占用、释放或转移 B 机的名额，也不把 A 的队列改投 B。此处是 Local Hand 执行容量规则，不承诺调用平台的连接数量、请求速率或同时发起调用的能力；连接验收仍按第 3.1 节进行。

为使“整机 5 个”可执行，首版每台物理机只采用一个可准入新业务的安装／执行域及唯一受保护名额池；多个前端或连接必须共用它。VM／WSL 是执行域选择，不因另起 node/install 自动增加五个名额；物理宿主归属须由受保护部署登记核实，不能只凭 guest 身份推定为另一机器。备用及旧安装不得独立启动新业务；受控 CLI、兼容 prepared 及其他业务启动入口须接入同一准入与计数，不能接入的入口拒绝首次执行。原任务仍按原绑定恢复／收尾，旧执行未证明退出时不能将名额池重置为空。本轮不新增多执行域间的宿主调度器。

这里的“首版”指本轮多账号与单机并发增量，不改写历史 v0.1 范围，也不沿用其验收结论证明新能力。队列只安排调用方已经授权提交的任务，不分解目标、生成新业务或创建通用任务依赖调度器。

执行与等待规则：

- 一个任务从占用物理准备资源起，到执行及采集进程确认退出并可安全释放资源，始终占一个名额。逻辑准备、排队、状态查询及旧成果读取不占执行名额；它们仍受各自容量和请求限制。存在未决进程的名额先核对，不能仅因超时或连接断开释放。
- 只有正式提交且获准的任务进入持久队列；聊天、查询、逻辑准备及重连不新增执行授权。整机满 5 个、同项目写资源被占用或暂时资源不足时等待，不能为了凑满 5 个突破 CPU、内存、进程及存储预算。不满足能力或权限、永远无法容纳的请求明确拒绝，不无限排队。
- 逻辑 prepare 返回不占物理名额的可提交意图及摘要；正式 submit 持久接受该意图。意图绑定主体、稳定 node/install、项目、准确输入／基线、获准能力约束、预算和等待期限。源快照固定 commit 及完整内容清单摘要，验证定义也固定版本／摘要，不能只保存可重新解析的 `source_ref`／`validation_ref` 名称。排队查询／取消绑定原任务及意图摘要；物理派发另保存 `request_digest` 与两者关联，两个摘要不互相替代或中途换义。重试相同身份及请求不重复入队，异内容冲突。队列接收与底层业务准入是两个不同的完成事实，响应必须区分。
- 队列按持久接收顺序选择满足项目与资源条件的任务；暂不能运行的任务不占执行名额，也不阻塞其他可运行项目。队列数量、字节和等待时间有界，满时明确返回；主体只能查询、取消自己的等待任务。取消与派发互斥，不能取消成功后又启动。到期／撤权处理不等待空闲执行名额；终结项退出可运行队列后，原身份、去重及终态关联继续保留并计入存储预算。

队列由该机器所选执行域的唯一受保护管理方持有权威状态。领取名额须先持久绑定原意图、名额及领取代次，再准备、启动；重启后的旧领取者不得对新代次执行。队列消费者代表原提交授权完成准确物理请求的业务准入，不能停在“启动控制器”后等待客户端再次在线。原意图 → 物理请求／名额 → 控制器启动 → 业务准入结果的关联均须耐久保存；响应丢失按原关联核对，不能创建第二个业务或尝试来猜测原状态。

当前授权、项目／能力约束、取消与期限在领取时、物理准备完成后及首次业务准入前重验，并由最终放行入口与撤销／取消使用同一权威状态协调。等待期限截止首次业务准入，领取名额不停止计时；进入业务后使用原执行预算，不以排队超时释放活动名额。只有持久禁止后续启动、业务尚未准入且相关准备／控制进程停止已证实，才能报告“启动前取消完成”。已准入或启动未知而尚无完整停止证明时，报告取消处理中／核对中；取得停止证明后可按原事实收尾，不改写业务结果。物理资源释放均须证明相关进程／写入者已停止且后续启动受阻，不以业务从未准入为条件。token 到期不等于已接受意图到期；不得保存用户 token 供自动派发，内部调用仍须受保护、绑定原主体及准入，不能伪造或扩大其 scope。

正式接受时，由可信认证入口形成并由权威管理方保存原主体、准确提交动作、有效授权上界及所用授权版本，绑定原意图；这些是受保护的授权记录，不是调用方自报的权限或留存 token。后台派发以“原授权上界 ∩ 当前许可 ∩ 原任务约束”放行。服务 UID 的维护权限或任务 policy 的全部 scopes 不能补成原用户的委托；等待期间新增权限也不扩大已接受意图。入口、管理方和任务控制器必须显式完成这一受保护交接，不能把 OS 对服务进程的认证当成最终用户授权；业务进程不得伪造或借用该交接。

同一项目的写任务默认串行，即使整机只运行一个任务，第二个同项目写任务也需等待。受保护登记将项目引用、不同源快照与成果应用目标映射到稳定的写资源身份；同目录、重叠目录、别名及已登记的共享可写输出归入同一互斥组，跨账号生效。不能仅用 `source_ref`、快照目录或 `repo.resolve()` 字符串证明互不冲突；无法确认分离时拒绝并行。调度与受控成果应用必须共用该登记。

上述项目互斥限于本机受控写域。不同机器上的同名项目若使用各自独立副本，分别占本机名额和项目锁，不按项目名称建立跨机锁。首版不支持多个执行节点共同写同一工作区、成果应用目标或直接可写输出；登记时须核实写域归属，不能证明独占的对应写能力不开放，不能将其误登记为互不冲突的资源。NAS 成果服务的 producer／store 隔离及受控事务继续按第 4 节处理；共用 NAS 不等于共用可写项目目录，也不提供跨机项目锁。本轮不新增分布式写锁。

项目执行互斥在原执行、采集及相关写入者确认停止后释放；封存成果等待采纳本身不持有项目锁或执行名额，因此原用户离线不应堵住整个项目。成果应用重新取得同一写资源租约，覆盖检查、写入、验证及最终观察，核对原基线、HEAD、索引和目标内容；冲突时保留结果、拒绝覆盖，不自动合并。现有本地应用是受信 CLI，依赖 OS／Node Profile 授权及事先核验的成果，不已经具备服务端的 OAuth 归属与当前项目授权检查。若将来由服务代为应用，须在受保护写入口补齐这两项检查；首版不因此新增自动应用入口。协作租约不等于能阻止任意外部编辑器写入。

执行结束／成果封存不等于代码已经合入项目。需要前一项修改的工作由调用方在其受控应用后，明确采用包含这些修改的新受保护源快照，再准备并提交。现有成果应用只更新目标工作区，不自动刷新登记快照；排队也不自动包含前一项成果。原已接受意图的准确源／验证定义无法保持时，须在证明业务未准入且后续启动已阻止后，记录为未执行的不匹配并保留原字节；新输入使用新的操作身份及明确提交，记录前后关联，不静默更新原输入／摘要。仅成果应用目标发生变化，而原源快照保持时，无依赖任务仍可按原输入执行；其成果向已变化目标应用时必须重新核对基线并拒绝冲突。没有结果依赖的其他请求不因某份成果尚未采纳而等待。

**实现边界：当前代码仍为单执行会话，尚未实现上述 5 个名额及整机队列。** 现有资源准入、取消与退出证明依赖共享父 cgroup 为空，不能只将 `max_active` 改为 5。实现须提供相互隔离、持久绑定的执行名额，保留配额创建互斥，核对整机及父级预算，并预留所有活动任务尚未增长的日志／管理存储；某任务的取消、退出或未知状态不得误控制其他任务。已有单任务后端的排队状态不能代替整机队列。

请求连接断开不等于任务取消。恢复先核对原任务及实际执行状态；确定尚未派发的原队列项只有在派发就绪、当前授权、期限和原约束仍有效时才继续。稳定意图不绑定未来未知的 boot；物理请求追加实际 boot／epoch／policy／名额绑定。普通重启或升级须显式判断兼容；不兼容项停止并说明原因。已有物理尝试只有证明业务未准入、旧启动者已隔离且原业务约束未变，才可追加新的环境绑定，保留旧尝试；仅查不到任务记录不构成此证明。已准入或启动未知的任务沿原身份核对，不重放。失败、未知、结果丢失均如实返回，不让健康节点接管离线节点任务。

### 3.5 同项目用户的任务隔离

项目授权与任务归属分别检查：用户 A、B 即使拥有相同项目、作业类型和 scope 授权，A 准备的任务仍绑定 A 的本地主体；B 不得接管其准备、首次提交或重试，也不得查询其任务状态、读取执行日志／成果清单／成果分块、取消任务或发起原任务核对。反向同样成立。知道 `operation_id`、artifact ID、摘要或分页游标不构成授权。

准备记录、受保护 manager、运行中控制器、退出后的只读账本与成果读取都须核对该归属；重启、恢复、重复提交、缓存命中和缓存丢失均不得绕过。拒绝必须发生在返回私有任务内容或产生控制副作用之前；不得修改原任务或按其他用户身份重提。原用户在权限仍有效时继续正常读取和操作自己的任务。

隔离单位是认证后映射出的持久 `principal_id`，不是 ChatGPT 账号显示名或连接名称。两个连接映射到同一个主体时共享其任务权限；需要用户间隔离时必须使用不同主体。首版复用既有 owner 检查，不增加任务共享、管理员代操作或复杂角色接口；并发按第 3.4 节的每物理机唯一名额池处理，主体及同名项目不形成跨机总池。

项目准入须贯穿能力展示、源文件读取、逻辑准备、入队、物理准备和首次业务准入。入口与受保护 manager 使用同一份当前、受保护且有版本的主体授权；复用既有 scope／profile／source 规则，不能用全局登记或调用方传入的“已授权”代替检查。任务执行策略只包含该任务获准使用的资源，不把其他项目的全局源清单复制给任务。授权读取失败不回退旧快照继续派发；保存原任务 policy 不等于当前仍获准启动新业务。

授权边界也必须覆盖任务进程对文件和本地 IPC 的访问。当前本地维护接口按 `SO_PEERCRED` 的 UID 映射主体；若多个任务继续共用 UID，仅有不同 cgroup、私有挂载命名空间或只读目录，不能证明其他任务的私有文件不可读，也不能阻止连接其 Unix socket。多用户上线前须用平台执行身份／文件可见性／IPC 权限落实跨任务隔离：业务进程不能直接读取其他主体的工作副本、日志或保留证据，不能调用其他任务的管理通道；受信管理服务的代理权限不得下放给业务进程。名额或执行身份复用时仍须保护旧任务文件及控制通道，不以复用 UID 转移历史权限。按选定后端做真实访问负向验收；保留固定验证代码的既有信任边界，不宣称任意恶意代码沙箱已完成。

项目读取授权允许看到共享项目中已接纳的代码，包括其他用户已应用的修改；它不开放其他主体的任务日志、私有副本、原始成果包或控制权限。仅撤销项目准入时，Local Hand 受控入口禁止新的项目读取、准备、派发和项目写入；本地 CLI 的 OS 文件权限及 Node Profile 授权须分别管理，不会因 OAuth 项目撤权自动消失。若主体未整体撤销且仍具相应历史任务 scope，可继续读取、取消或核对自己的旧任务。整体主体或相应 scope 被撤销时拒绝对应访问，不回写旧任务所有权。派发拒绝不妨碍管理方按原绑定完成停止与资源收尾。

这里的当前撤权以节点受保护的主体／scope／项目授权及撤销记录为准。IdP 登出、禁止刷新或单连接断开，不证明已签发 JWT 立即失效，也不自动取消已接受意图；当前 JWT 校验没有逐会话注销查询。需要立即禁止新的业务准入时，须落实节点本地撤权；运行任务的停止另按原授权取消流程处理。

实施沿现有 resident／manager 链补齐以下交接，不另建统一身份平台：

- 唯一受保护 manager 持有节点当前主体、scope、项目许可和撤销状态及其版本；变更与最终首次业务准入按同一权威状态串行判定。撤权先完成则禁止准入；准入先完成则按已接受任务处理，需要停止时走原取消链。入口过滤不能替代 manager 在读取项目文件、启动及最终准入前的检查。
- 可信入口先验证当前网络令牌，再通过与业务身份隔离的 IPC 传递版本化授权封套：目标 node/install、主体、准确动作、目标项目或原任务、请求／意图摘要、原有效 scope 上界、授权版本、单次调用身份和接受截止时间。截止不得晚于原 token 到期；manager 在截止前核对受信发送方和完整绑定并接受，未接受的过期／迟到封套拒绝，重复调用沿原接受事实核对，不产生新的授权或业务。接受的执行意图耐久保存该授权记录；普通同步查询和取消也完成交接，但不因一次读取就建立后台执行授权。接受期限不等于业务完成期限，已接受任务按原预算与第 3.4 节处理。
- 当前同步调用及未来队列均使用“原授权上界 ∩ 当前许可 ∩ 原任务约束”；前端在实际交接前重查 token 有效性，manager 在执行对应受保护动作前重查当前许可和 owner。已接受意图按第 3.4 节继续，不保存 bearer／refresh token；授权存储不可读、状态连续性不明时拒绝新的受保护操作，保留管理方按原绑定收尾的能力。
- 当前 `Broker.revoke()` 还会为其账本中的非终结任务设置取消请求；它不是统一 resident 授权库，也不是仅撤销项目准入的接口。新增项目授权管理须区分上述两种动作，保留旧接口的明确语义，不用改文档把现有取消副作用消除。旧协议未携带原授权证明的首次执行不能静默进入新的多主体模式；保留原任务读取与核对兼容。

上述为必须满足的产品规则，不代表多账号部署已验收。常驻入口的按主体项目授权仍须补齐，不能把任务 owner 检查通过等同于整个多用户授权链已经完成。

## 4. NAS 成果归档：最小新增实现

### 4.1 仓库责任与接入方式

Local Hand 增加有界归档 outbox、上传／核对客户端，以及原任务到成果引用的映射。优先扩展现有 `artifact_archive.py` 与相关证据路径，不另建执行系统。

Ledger 增加可选的固定归档接收／查询／读回适配层，复用其公共 `execute`、`get_operation`、`get_record`、`read_blob`、`verify`；不复制事务逻辑，不让 Ledger 核心依赖 Local Hand 私有任务字段。

优先采用受认证 HTTPS 固定接口；如果现场已有同等受限、可审计的固定入口，可在实施清单中明确替换传输。必须在实现前固定传输、认证、资源限制和恢复契约，不能以“抽象接口”代替它们。该入口不是新的 Local Hand、通用远程 shell、任意 Python 执行或共享 SQL 接口。

首版目标图采用明确主路径：**接收端运行在 NAS 内受控环境，Ledger 库位于 NAS 自身经过验证的可靠本地文件系统**，由一个逻辑写入者提交；客户端不通过 SMB/NFS 直接打开数据库。实际 NAS 是否具备此运行条件需要现场验证。

若改由独立存储宿主承载接收端和本地成果库，必须另列“宿主 Ledger 已提交”与“NAS 已发布并读回验证”，完成后续 A2 快照发布／回读才可称 NAS 保存。前者不能冒充后者，图也必须增加宿主到 NAS 的实际链路。接收宿主不得必须依赖另一执行节点，否则不能宣称该归档路径独立于执行节点。

NAS 若不具备运行接收端的条件，可以先复用已有“本地成果归档 + A2 封存快照发布”作为明确标注的过渡能力，但这不算在线多客户端归档目标已经完成。无需重做已验证的 Ledger A2。

### 4.2 受保护目标与权限

- 部署配置保存目标、信任材料、存储身份、绑定版本、允许的 producer 和成果库；业务任务只能引用已批准的 `storage_ref`，不能提供任意 URL、挂载路径或凭据。
- 服务端由认证主体映射 producer 和授权成果库，不信任请求中自报的节点名字。`namespace_ref` 只是数据，不是鉴权。
- 初版不共享跨 producer 的可写库。需要跨节点读取成果时，单独授予只读范围；不因使用同一 NAS 自动放开。
- 收到请求先验证身份与目标，再按长度、条数、单体和累计预算有界接收；有界排队并限流。沿用 Ledger 实际内容上限，不能用流式上传绕过单项或总量限制。
- 身份／权限失败不轮换到其他主体重试；网络超时与服务暂不可用采用有上限退避和稀疏日志。

`producer` 由受保护登记固定绑定原 `node_id + install_uuid`，不使用机器显示名或令牌值代替。真正新安装登记新的 producer；普通凭据轮换保持原 producer／store，秘密通过独立受保护引用更新，不改归档 key，也不继续使用已撤销的旧凭据。现有归档 scope 只绑定 `(producer, operation_id)`，因此这一安装作用域约束必须在生成新归档前生效；历史 producer、原请求字节和 scope 保留，通过显式兼容登记关联，不以新字段重算旧身份。

普通节点操作面只含目标身份／限额发现、原 create／append 提交、原幂等请求查询、授权记录与 blob 读取。初始化、恢复、导入、删除、库路径选择和服务管理留给独立运维入口，不因归档权限一并开放。

### 4.3 outbox 与幂等契约

以下是拟新增设计，不是当前已实现的自动归档能力。

1. 对需要保证成果保留／归档的任务，准入时预留本地耐久空间并记录归档意图；空间不足拒绝新增任务。
2. 首版沿用当前归档消费者的准入：`TERMINAL / EXITED / SUCCEEDED / SEALED`。符合条件的原任务发布 outbox 项；失败、取消、UNKNOWN 的执行记录和可用证据保留在原节点并如实返回，不宣称已覆盖其 NAS 归档。扩展这些成果类型须单独定义映射与负向测试。项内保存完整原任务来源、封印、不可变内容或受保护引用、长度／摘要、完整逻辑目标及绑定版本。
3. 一次生成并持久保存 Artifact、Version、Blob 等 ID，保存原 create／append 请求字节、各自原生幂等三元组与指纹。归档 operation 与业务 operation 明确区分。
4. 相同幂等身份只能接受相同指纹；内容摘要是被绑定的值，不能把变化的摘要加入 key 来掩盖冲突。首版不增加独立异步接收队列或第二份提交真相；诊断 correlation ID 不替代 Ledger 原三元组。
5. create 和 append 是两个事务：create 成功、append 未知时保留前者，沿原 append 核对；不能假称二者可以整体自动回滚。
6. 用原目标、原 key 核对原回执，并对准确版本、长度和真实内容摘要读回验证。仅收到 HTTP 200、metadata 或 marker 不算“成果已归档且可核对”。
7. 确认与保留条件均满足后，只回收允许删除的本地内容并释放其实际占用；未确认、未知或被保留的项不得因清理或升级消失。

待上传内容与长期归档索引分开管理。原任务到完整存储绑定、准确成果／版本、原请求字节及指纹、回执的关联必须耐久保留；查询或重复归档不能把 outbox 项消失当作从未归档，重新生成 ID 或请求。这些保留记录也计容量；到达上限时停止相应新增准入，不删除幂等历史腾空间。

释放本地内容前，必须实现并验收经原节点、原绑定的受授权准确读回，按原封印核对内容；未满足时保留本地可读副本。当前 `artifact_archive.py` 的恢复仍依赖完整本地目录，不能直接删除文件来实现清理。释放后，任务状态仍可本地查询，但证据内容可能依赖 NAS；NAS 不可用时如实返回内容暂不可取，保留过去的确认事实，不重跑业务。图中的返回箭头表示经原节点返回，不保证所有证据永远无需访问 NAS。

接收端的最终持久化与幂等提交以 Ledger 原事务为准，保留原 `commit_state`、`result_ref` 等字段语义。单个节点只有一个受互斥保护的归档消费者；所有待发送、失败、未知项和中间文件都计入节点／项目字节与条数预算。不同目标公平轮询，某目标超时不得永久阻塞其他目标。对重试次数、单次超时和日志速率设限，达到自动重试预算后保持待人工处理状态，而不是丢数据。

服务端还须为每库及服务总体设累计准入上限，覆盖存量内容、记录数、原请求／幂等历史、接收暂存和备份／恢复开销。上限取所选提交、检查点、备份、恢复和核验链能共同处理的范围，而非 NAS 剩余空间或单请求上限；准入预留须与并发提交互斥。当前消费者恢复依赖全库 `export_bundle`，其总量限制与 A2 快照限制不同；P1 必须固定实际恢复路线和安全余量，验证多次合法追加后的边界。达到上限前背压，不自动换库、改目标或删除历史绕过；扩容须先证明对应恢复链可覆盖新增容量。

发布终态、封存证据、发布 outbox 并非天然一个事务：必须保存可恢复意图，以原任务身份识别“已封存但未入队”和“已确认但未清理”，补齐归档步骤；恢复扫描不得调用业务 submit。每个崩溃窗口均须注入测试。

### 4.4 成功与失败分别表示

保持三个独立维度：`business_outcome`、`evidence_state`、`archive_state`。下列归档状态名称为拟议设计；实施时以版本化契约固定。

| 事件 | 处理与可报告事实 |
|---|---|
| 归档尚未确认时 NAS 不可达 | 保留本地证据；未发送项保持 pending，可能已提交项保持 unknown；业务成功不冒充归档成功，不重跑业务 |
| 归档已确认后 NAS 不可达 | 保留过去确认事实，另报当前内容可读性；已释放本地内容时不伪造可读，也不降回待归档或重跑 |
| 接收提交后响应丢失 | 归档 unknown；查询原请求，必要时只重送完全相同的归档请求 |
| 原请求查询 NOT_FOUND | 不是永不提交的证明，原请求可能仍在执行；不得换 key／目标规避 |
| 回执匹配，但内容不可读／损坏 | 不能报告 verified；保留损坏／未知事实，不自动重写既有版本 |
| 本地 outbox 满 | 对需保证证据／归档的新任务背压或拒绝，不删除未知项腾空间 |
| NAS 满或权限改变 | 分清明确未提交、已提交、未知；不循环创造新成果 ID |
| 更换 NAS 绑定 | 新任务可绑定新版本；已发送／未知项继续核对原目标，不自动迁移或双写 |
| NAS 恢复到旧快照 | 使用显式恢复绑定／库世代，核对回执与幂等历史；不能凭同一 URL 假定历史完整 |
| 本机状态盘丢失 | 停止新写入并进入恢复流程；不能静默创建空状态库继续使用旧节点身份 |

NAS 故障可以影响共享它的多个节点的归档，这是明确的共同故障域，不是执行节点相互依赖。只有任务本身需要 NAS 输入／远端提交，或本地保留预算耗尽时，才阻断相应新任务；不能承诺无限离线工作，也不能把所有任务启动都绑在 NAS 健康上。

恢复到旧快照后，分别保留“过去已确认的原回执”和“目前成果缺失／不可读”的事实；不回滚本机业务状态，也不把旧任务重新列为待执行。若需恢复原成果，只按显式恢复流程使用原封存内容，不重新执行业务生成替代品。

恢复换代先关闭旧写入入口、确认在途写入结束并阻止旧写入者继续提交，再核验所选恢复点。以追加式恢复绑定记录原目标到新世代的映射及核验依据，原 outbox、请求与回执不原地改写。只有明确纳入恢复绑定且已核对原幂等历史的请求，才可经新世代查询或按恢复规则继续同一归档请求；缺失已确认历史不能解释成从未提交。旧世代写入须被拒绝，延迟回执仍按其原世代核对，不能冒充新世代当前完整性的证明。当前 `bind_restored` 要求匹配受信检查点与完整历史，不能把它当作接受任意较旧快照的现成能力；超出已证明恢复范围时保持只读／待处理。

## 5. 跨平台实现与发布

第一版各目标平台必须交付相同的最低作业面：`host.inspect`、已登记项目的受限 `workspace.edit` 及其固定验证，以及 prepare／submit／query／cancel／证据读回／原任务恢复。项目、工作副本、验证命令和输出预算逐平台登记。固定验证不是任意命令执行入口。

任一平台只有能力发现、或缺少上述共同必需能力，都只能算受限候选，不能算该平台版本完成。GPU 作业、NAS 新业务作业、任意 shell 和跨节点任务迁移不在该共同能力承诺内。

### 5.1 先验证高风险路径，再抽接口

保留 Linux 现有行为，按实际需求抽取：受保护文件、实例互斥、本地 IPC、时钟与生命周期身份、manager 绑定、进程树控制、工作区隔离、存储预算，以及状态／配置／outbox 的锁、原子发布和耐久性。`artifact_archive.py` 的 fcntl、POSIX owner、目录 fsync 等也需适配。配置选择后端，请求方不能任意指定后端或放宽约束。

现有 `manager_binding.py`、`runner.py`、`task_session.py`、`budget.py` 与受保护管理服务带有 Linux 假设。新增带平台判别的版本化绑定／证明，保留旧记录解码，不能给 Windows 伪造 cgroup、UID、device/inode 或 Linux 启动身份。

### 5.2 Linux ARM64 与 x86_64

- 基线中的 `tests/e3_host/q2_prepare.py` Quota 路径限制 x86_64。当前源码候选已为该路径及容量核验器 `q2_core_delivery_dispatcher.py::_CapQuota` 增加小端 LP64 aarch64 的类型宽度、对齐和逐字段偏移检查，并以同一原生 C 头文件探针对照验证。两者都要求 GET／GETNEXT 返回完整有效字段；容量观察仍禁止写入命令，原受控准备写入边界不变。这只解决所述入口的 ABI 与返回校验问题，不代表真实配额、其他原生 helper 或完整 ARM64 部署通过。
- 原生编译 ABI probe 和 native helper，核对结构大小、字段偏移、字节序与系统调用，再在获准隔离文件系统上验证字节／inode 配额、继承、保留任务占用及重启恢复。C helper 有 aarch64 分支不等于整条 prepare 已通过。
- 验证实际文件系统、配额挂载、设备和文件系统身份；不要直接更改生产根盘。缺少条件就拒绝相应能力或先准备获准专用存储。
- 验证 DMI／替代主机身份与执行域绑定；ARM64 不一定具有与 x86 相同的 DMI 来源。
- 当前受保护 prepare 复用测试目录 helper：应抽出单一生产实现并让测试复用，或作为受校验安装载荷明确交付，不能依赖偶然存在的开发目录。
- Linux x86_64 保留现有后端行为，并回归上述接口抽取涉及的准入、准备、执行、取消和恢复链；一个部署的验证不自动证明其他内核、文件系统或执行域受支持。

### 5.3 Windows AMD64 原生

- Windows Service 常驻，无需桌面登录；受限账户／令牌、ACL/SID、受认证本地 IPC、受保护配置与单实例锁。
- 进程在约束建立后才开始业务执行；实现 Job Objects 与进程树管理、取消、停止证明、管理服务异常后的原任务恢复。Job Objects 不是完整安全沙箱，必须防止 WMI、服务、计划任务等旁路创建未受控进程；不能仅靠一次通知证明全部退出。
- 首版选择保守策略：受保护 manager 持有不可被任务继承／复制的 Job 控制句柄，最后受控句柄关闭触发进程树终止；manager 崩溃后核对退出与原任务，保留失败／未知，不重放。MCP 与 manager 分进程，单独重启 MCP 不应关闭管理句柄。此策略必须在 P1 证明；不能同时承诺 manager 崩溃后任务一定继续。
- 路径测试覆盖盘符、UNC、大小写、长路径、hard link、junction 和 reparse point；授权检查和实际打开对象必须一致。
- NTFS 用户／卷配额不是 Linux 项目目录配额。固定容量任务卷可作为候选，但还须证明文件数量／元数据、临时文件、日志、证据和保留任务边界；不能默默删掉 `storage_inodes` 等承诺。若只能提供不同约束，应新增明确能力 profile 和契约，不宣称等价。
- 替代存储 profile 必须给出可强制的字节、对象／元数据、临时与管理开销上限及限制；缺少共同必需的资源保障就不能公布对应作业能力。Windows 安装态须同样通过 outbox 崩溃／原子发布／耐久性测试，不能只复用 Linux 协议测试。
- P1 还须逐项固定 CPU、内存、进程／线程、时间和存储预算的统计对象、执行阶段、强制点及超限行为。当前 Linux 的 `processes` 映射为包含线程的 `TasksMax`，不能直接换成 Windows 的进程数量限制；CPU 时间／速率、内存统计也不能凭同名同数值宣称等价。通过线程洪泛、多进程合计 CPU／内存、绕向任务卷外可写目录的负向测试证明边界；差异必须进入版本化 profile，不能降低共同保障而仍报兼容。
- 区分 OS 启动、服务世代、任务执行实例与时间预算；明确挂起／休眠是否计时，测试 Fast Startup、恢复和墙钟回拨。服务重启生成的 UUID 不能冒充 OS boot ID。
- 初始原生验证目标为 Windows 11 AMD64；其他 Windows 版本另行说明支持范围。WSL／VM 可作为另选执行域，但不冒充 Windows 宿主原生能力。设备具有 GPU 不代表已支持 GPU 作业；驱动、计算运行时、GPU 权限和固定作业 profile 需另行准入。

参考：[Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)、[Job 基础资源限制](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information)、[systemd 资源控制](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html)、[NTFS 配额策略](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-admx-diskquota)、[Windows 时间语义](https://learn.microsoft.com/en-us/windows/win32/sysinfo/windows-time)。

### 5.4 同版本，不同安装制品

一个版本号与 source commit，对应 Linux x86_64、Linux aarch64、Windows AMD64 各自的依赖锁、wheel、原生 helper、受保护管理载荷、安装／卸载／回退程序及能力证据。先核实每个部署的操作系统、架构及实际执行域，再选制品。

当前 wheel 包清单不足以独自交付完整受保护 prepare／管理链。发布 manifest 必须覆盖全部运行载荷、Python ABI、依赖与文件摘要；每台在没有源码工作区的干净安装环境验证。构建锁不可直接跨架构套用。

升级可分别进行；只要求明确协议兼容范围，不要求各节点同步重启。不兼容版本明确拒绝操作。旧任务以原协议／原身份查询，不通过重新执行产生“新版本结果”。

## 6. 启动、认证与网络独立性

### 6.1 沿现有版本确定部署单元

本方案采用逐节点独立部署完整接入链：每个节点分别部署 OAuth/OIDC 身份服务、HTTPS／网关或隧道入口、MCP 资源服务器及本地管理服务。这是本次部署选择，不是要求所有 Local Hand 安装内置身份服务。身份服务负责登录、令牌签发／刷新和 JWKS；Local Hand 只实现令牌校验、主体映射与任务授权。“外部 issuer”是软件边界，不要求放在另一执行节点。各节点分别管理认证状态、签名密钥、客户端注册与 resource audience；共享产品代码和部署模板，不复制密钥或任务身份。

每台物理机按第 3.4 节采用的唯一安装／执行域部署一个独立授权服务器实例，服务该节点的多个本地主体、项目及连接；不按账号、项目或 worker 再建实例。实例的数据库、签名私钥、会话和客户端注册状态位于本机可靠存储，与业务 UID、任务工作区及 NAS 成果库隔离。认证配置可以复用无秘密模板，运行状态不跨执行节点共用。

本次细化以源码 `31411551b1f5bbac1f6bdf7b032cd4a0b3bdab22` 为核对基线，保留第 1 节和历史验收原基线。`tools/local_hand_mcp/auth.py` 已提供 `lh-mcp-auth-v1` 的单 issuer／单 client、多 subject 映射；`server.py` 发布受保护资源发现并接入校验。这些是资源服务器能力，尚没有授权服务器安装器或独立认证部署验收。当前全局项目登记、内部授权交接及业务身份隔离的缺口仍按第 3.5 节完成。

具体身份服务的上游实现、准确版本／镜像摘要、部署清单、持久化与恢复入口必须能从部署记录定位；`--auth-config` 和测试 issuer 不能代替该服务的部署交付。DNS、证书签发／续期、隧道控制平面等共同外部依赖单独声明，不由另一执行节点隐式承载。NAS 的存储职责不自动赋予其统一登录中心职责。

### 6.2 部署清单与协议兼容

优先核对已采用的上游产品与可重建版本，再复用其获准部署方式；不凭 URL 风格猜测产品，不在本仓自研密码验证、登录、授权码或刷新服务。所选平台缺少可用制品或不满足下列契约时，记录具体差异后调整，不能用测试签发端补位。公开仓库保存通用契约及无秘密模板；实际采用值与恢复入口在私有部署记录中维护。

| 必须登记的对象 | 实施与核对要求 |
|---|---|
| 上游及安装入口 | 官方来源、准确版本／制品摘要、平台架构、启动与停止清单、配置模板及备份／恢复命令的位置；未定位者标为待核实 |
| 运行与存储 | 服务 OS 身份、权限、可靠持久目录、密钥／数据库／会话保存方式、容量及备份保护；业务进程不能读取或修改 |
| 网络与信任配置 | 本节点唯一 issuer、发现／authorization／token／JWKS URL、MCP resource audience、HTTPS 路由与证书、必要代理和共同外部依赖；分别记录浏览器、MCP 客户端后台与本机服务实际使用的路径 |
| 客户端登记 | 复用预注册 public client、授权码及 PKCE S256；精确 redirect URI 白名单、获准 scope、访问／刷新有效期及刷新重放处理；不因两个账号增加多个 client 或启用任意动态注册 |
| 身份与授权映射 | 当前 issuer 下的 subject → 持久 principal；主体到项目／scope 的当前许可、撤销状态与版本；不是按用户名、连接名或客户端 ID 授权 |
| 恢复与切换 | 配置版本、状态一致性备份、旧快照的撤权／会话恢复屏障、唯一启用实例、独立维护通道、切换和回退步骤 |

客户端登记中的 token endpoint authentication method 为 `none`，仍须实际登录、授权码兑换和刷新验收；不能以 issuer-wide methods 列表是否列出 `none` 推定这一客户端配置。每个节点分别注册应用，应用 ID 即使同名也不共享凭据、会话或任务权限。

保持当前验证器的真实访问令牌契约：RS256／ES256 白名单、准确 `iss`、等于该节点 resource 的单字符串 `aud`、准确 `client_id`、已映射 `sub`、有效 `iat/nbf/exp` 和获准 `scope`；使用所配置的最大寿命、时钟偏差和文档读取预算。真实上游签发必须逐项满足，不能把 `azp` 当成缺失的 `client_id`，或放宽成接受多个 audience。该部署将应用 client ID 与 MCP resource 区分；ID token 不可当 access token，须用上游真实 ID token 做拒绝验收。当前允许 `JWT`／`at+jwt` 类型，不据此宣称完整实现某一 JWT access-token profile。

MCP 的受保护资源元数据只指向本节点预配 issuer；发现结果须与受保护配置匹配，不随响应改换可信 URL。AS 负责刷新轮换／重放拒绝、会话及有效期，MCP 不持有用户 refresh token。登录、刷新、访问令牌验证、当前本地授权分别报告：AS 登录成功不证明项目获准，AS 登出或禁止刷新也不证明既有访问令牌立即失效。有效缓存内的令牌验证仍按原 TTL／时效规则处理；需要立即限制访问时使用第 3.5 节的本地撤权，不把 AS 临时不可达当作撤权证明。

协议依据为 [MCP Authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)、[RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html#section-2)、[OAuth 安全最佳实践](https://www.rfc-editor.org/info/rfc9700/)及 [OIDC 主体稳定性](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability)。这些依据不替代对所选制品和实际客户端的兼容验收；依赖版本不因本次设计修订而升级。

### 6.3 启动与故障行为

每台把本地安全恢复与网络新准入分开：

1. `系统启动 → 本地身份／状态盘／互斥检查 → 受保护管理服务与原任务恢复`。默认关闭新业务准入；本地维护通道仍须验证操作系统身份与权限，只用于核对原任务、收尾及获准的停止操作，不重新提交业务。
2. `系统启动 → 身份服务的持久状态／密钥检查 → 本机代理（需要时）、身份服务及 HTTPS 认证路径启动 → 经预配 URL 核对 discovery／JWKS → MCP 启动 → 机器可执行的认证／路由就绪检查`。只有管理服务就绪、权限和依赖检查均满足后，才开放获准的新业务准入及队列派发。

两支可以并行。issuer／JWKS 不可达不得阻止第一支启动，也不能成为第二支放行未认证请求的理由。本机身份服务与认证路由不得反向等待 MCP 健康；共用网关进程时，也必须在 MCP 未就绪时提供认证路径，避免 MCP 等待 issuer metadata 而网关又等待 MCP 的环路。安装、切换或相关配置变更后，另从实际外部入口验收用户登录、刷新、连接和节点身份，确认对外可用。这项需用户参与的验收不作为每次开机的交互式门槛，不要求原已授权队列等待用户重新登录，也不为此保存用户 token；机器就绪检查不冒充端到端验收。启动前不检查尚未启动的自身 MCP 入口；本地恢复、网络认证就绪与外部可达分别报告。

当前 `server.py` 的启动钩子只核对 issuer metadata，JWKS 在首次令牌校验时读取。实施须另补部署就绪检查，核对可信发现／JWKS、配置代次和实际路由，不能把 ASGI 启动或 HTTP 200 当成签名链、用户登录或多主体授权已经验收。检查使用公钥及非秘密元数据，不为每次开机保存用户令牌；私钥签发、刷新与完整工具调用在安装／切换验收中证明。

需要代理的部署分别使用获准的本机配置，不复制其他节点的身份或凭据。后台核心先在隔离端口验证，再安排端口唯一所有者和受控切换；不能以桌面登录后的交互式自启动代替系统服务。

HTTPS 检查使用实际服务用户与其网络／代理设置，验证 TLS、预期响应及必要认证。清单分层：MCP 网络入口启动前只检查真正必要的外部依赖（如身份发现／JWKS）；启动后核对本机认证与实际外部 MCP 路由；任务特有端点在对应任务准入／执行阶段检查，不能阻断无关任务和可安全完成的原任务恢复。浏览器可上网或端口开放不算通过。`auth.py` 的 HTTP 客户端使用 `trust_env=False`，故仅设置 `HTTPS_PROXY` 不足；当前源码候选提供受保护的可选 `document_proxy_url`，仅作用于认证文档读取，回环地址直连且保持 TLS 验证。配置与回退说明见 [使用说明](USAGE.md#job-service-deployment-inputs)，实际服务用户和外部入口仍须现场验收。

每次检查有超时，失败有间隔与退避，日志限速；启动互斥避免重复实例。恢复核对原任务和原归档；已证明未派发的原意图在机器就绪、当前许可及原期限满足时按第 3.4 节继续首次派发，不重放已准入或未知业务。NAS 归档消费者单独恢复，不作为不相关任务的全局启动前置条件。

外部入口或认证刷新失效时按策略拒绝新的未获准操作，不自动停止或重提已接受任务；原任务管理与网络就绪状态分开。身份校验不得为保持可用性而失效放行。

代理配置保留 localhost、127.0.0.1、::1 直连与正常 TLS 校验。部署若包含桌面客户端，应分别验证桌面启动和命令行启动的实际网络环境；不能仅凭交互式 shell 配置推断客户端可用。

逐项盘点 DNS、证书签发／续期、issuer/JWKS、反向代理／隧道、网络出口、密钥保管、项目路径与状态盘的宿主。未发现源码硬编码其他节点，不等于部署无依赖：若一个节点的认证或入口仍由另一执行节点承载，必须解除该依赖或明确标为不满足独立部署。公共外部服务可成为声明的共同依赖，不能隐藏。

验收时逐一关闭或隔离另一执行节点，在待验节点无旧登录会话的条件下完成真实外部登录、令牌获取／刷新、服务冷启动、新任务准备／提交／封存读回及原任务恢复；再交换节点验证。核对各阶段使用的认证与网络端点，不能以有效旧令牌、JWKS 缓存或本地 CLI 成功代替外部链路独立。离线节点自身的入口不可达是预期现象，只有其他节点被它阻断才证明跨节点依赖。故障发生时保留原任务和未知事实，不自动转移或重放业务；仍保留第 3 节的原主体连续性与错节点拒绝要求。

### 6.4 issuer 切换、密钥轮换与恢复

沿第 9 节执行受控切换：先定位现有服务并保留一致性备份，在独立端口／身份安装候选并验证协议；随后暂停网络新准入及队列领取／派发，核对在途任务，记录配置与状态切换点，再切换唯一可信 issuer 和主体映射。更换 issuer 不改变 node/install、原任务 owner、请求、账本或封存字节；新旧 `(issuer, subject)` 的主体连续性须单独核实并记录，不能自动接受同名账户。新节点创建独立密钥和会话，不导入另一节点的私钥或 refresh token。

`AuthConfig` 当前启动时读取且不可变，写入配置文件不等于生效；按配置代次受控重载／重启并核对实际加载值。切换后的旧 issuer 令牌明确拒绝，客户端重新完成本节点登录授权；不增加自动双 issuer 信任或失败回退。恢复与保留读取仍走受保护本地通道，不借切换重提已执行业务。

同一 issuer 正常轮换密钥时，先发布新公钥并验证各校验方能在原 TTL／刷新冷却规则内取得，再启用新签名；旧公钥至少保留至最后一次使用旧私钥签发的时刻加上允许的最大令牌寿命及时钟偏差。不能以延长失效缓存维持可用性。紧急撤销泄露密钥时，先暂停网络受保护访问，受控失效各验证器缓存及尚未接受的旧授权交接，再核对旧签名确实拒绝后恢复入口并要求重新登录；本地原任务管理保持可用。仅从 AS 删除旧公钥或撤销会话不能使当前 TTL 内的缓存立即失效，具体处置须部署验收。普通用户撤权使用本地授权和 AS 会话控制，不靠全节点换钥代替。

AS 状态恢复须同时核对主体映射、客户端注册、密钥及会话／刷新状态，并保留最新节点授权和撤销记录。旧快照可能恢复已撤用户或刷新会话；无法证明连续性时保持新准入关闭，先隔离／失效旧会话并重新核实当前授权，再开放。不得用认证备份覆盖任务账本，不得用旧权限快照补齐缺失的当前许可；仅递增版本号不是连续性证明。具体上游的会话失效和恢复步骤必须在采用记录中实测，不能把“备份可解压”报告为可安全恢复。

## 7. 按交付物推进

当前先闭合首个采用节点的独立认证与当前授权：定位上游部署 → 固定第 6 节采用清单 → 补齐第 3.5 节主体项目授权、内部交接与必要 OS 隔离 → 安装态登录／刷新、越权拒绝及旧任务读回。这个增量保留现有单执行名额；双主体业务只有相关隔离与授权验收通过后才开放。随后按原目标接入五执行名额、持久队列与项目写互斥，完成第六项自动派发。临时五进程探针不代表任一产品增量已完成。已有适用的平台和单任务证据继续复用；不以其他操作系统、第二节点或 NAS 在线服务完成为本轮前置。下表保留完整规划，各增量分别经过受影响的阶段，不要求先完成整个并发方案才能验收独立认证。

| 阶段 | 交付内容 | 进入下一阶段的证据 |
|---|---|---|
| P0 部署条件与契约确认 | 本轮固定多项目授权、逻辑意图／物理请求协议、写资源登记和五名额预算；确认物理宿主到唯一启用执行域／名额池及全部业务入口的映射；归档线确认存储绑定 | 各线分别核对实际 OS／权限／文件系统／网络条件及写域归属；不把假设填为已支持，NAS 未就绪不阻断独立节点工作 |
| P1 高风险隔离验证，可并行 | 本轮验证独立名额、业务进程跨任务文件／IPC 拒绝、配额并发准入、项目互斥及取消／领取／业务提交崩溃窗口；其他平台验证 ARM64 quota ABI、Windows 隔离；归档线验证接收与恢复容量 | 受影响的原生边界及负向测试通过；多任务不超卖或互控，不因同 UID 或名额复用越权；恢复链覆盖累计准入上限；不支持项明确拒绝 |

| 容量与排队 | 本地／NAS 满、项数超限、慢上传、超大请求、重试风暴；多次合法追加／并发提交跨越全库恢复上限 | 有界内存／磁盘／队列／日志；预留与提交不超卖，准入容量可备份／恢复／核验；未知证据保留，新增任务合理背压 |
| 崩溃窗口 | 封存前后、入队前后、接收提交后、确认与清理之间 | 恢复原归档链，不丢唯一证据，不调用业务 submit |
| 清理后读回 | 已确认内容清理后重启、旧任务查询／读回、重复归档、NAS 离线 | 原映射／请求／回执保留；准确内容可核对，离线时不伪造可读；重复归档不新增写入，保留记录仍计预算 |
| 存储恢复 | NAS 旧快照恢复、库世代改变、在途旧写入／延迟回执、凭据轮换后核对 unknown、挂载身份不符 | 原绑定与恢复映射可核对；旧写入者受阻，延迟回执不证明新世代完整；不重算 key、不自动双写／切目标、不静默建空库 |
| 启动链 | 无桌面登录冷启动、issuer 不可达、代理失败恢复、JWKS 刷新、服务账号 HTTPS；用户离线且有未派发意图 | 断网时本地原任务恢复仍可用；就绪后按原授权派发不等用户重登，不重放；保留依赖与授权、TLS 和回环直连，机器检查不冒充外部用户验收 |
| 安装与回退 | 无开发 checkout；逐机滚动升级；切换时已有排队／领取／未决项；旧记录读回 | 停止接收、领取与派发，旧调度者受阻；只由兼容版本接管写入，保留原代次及状态；回退不重放任务 |

验收分层：静态／编译检查 → 单元与协议负向测试 → 平台原生隔离测试 → 安装态测试 → 实际部署与联合链路。每层记录准确 commit、制品摘要、环境、命令、退出码及原始输出位置；SKIP、unsupported、timeout、unknown 不改写成 PASS。公开报告只保留适合披露的能力结论和制品身份，凭据、实际设备映射与原始部署证据保持私有。

完成后按实际返回状态反查链路：所有任务核对返回状态 → 原任务身份／请求 → 执行绑定／权限 → 指定连接；声明 `SEALED` 才要求证据清单、封印与内容一致；声明归档已核验才追加准确成果版本 → 完整存储绑定 → 原归档请求／回执 → 实际读回内容。失败、取消、UNKNOWN 或未归档结果不要求凭空补出封存与归档证明；过去已核验与当前可读性分开报告。对应声明无法核对时，不能用“进程运行”“有文件”“HTTP 200”替代。

## 9. 部署与回退边界

实现阶段先使用隔离目录、身份、端口、合成任务与受控测试成果库。现有环境、安装和历史证据的保留或迁移须有明确清单；新部署不得隐式恢复旧执行入口或重放原业务。

部署验收按节点推进：备份配置和一致性状态 → 安装候选 → 隔离链路验证 → 记录切换点 → 切换唯一服务实例 → 在线验证 → 无桌面登录的重启验收。代理和远程入口切换必须保留独立恢复通道；重启验收采用明确维护窗口，不以丢失管理连接作为成功证明。

维护切换或回退前暂停新入队、名额领取及自动业务派发，隔离旧调度者并核对在途任务；保留新旧任务状态、领取代次、授权及归档请求。只恢复兼容的程序与配置；不理解新队列或隔离登记的旧版本不得接管写入，不用旧快照覆盖较新的任务库或幂等历史。无法安全回退时停在只读／恢复模式，不重新执行业务。NAS 的回退是独立、显式的存储恢复流程。

认证回退同样遵循第 6.4 节的主体／撤权／会话连续性。程序可回退不代表旧认证数据库可直接恢复；旧身份服务不可达时不得自动重新依赖另一执行节点。若另行明确采用原远端 issuer，应同时撤回“逐节点独立认证已完成”的声明并保留变更事实，不能把临时回退写成目标架构仍已通过。

实施所需的部署条件包括各节点访问权限、Windows 服务／隔离存储所需管理员权限、Linux 获准的配额文件系统、独立认证及入口配置，以及 NAS 接收端能力和存储授权。缺少时报告具体条件，不借用其他节点身份或绕开安全检查。

本文与图稿不构成运行态完成证明，也不自动授权新增 GPU 作业、跨节点任务转移、共享可写状态或 NAS 任意执行。

## 10. 设计校核与实现接续

方案和图稿应保持以下一致性：

- 调用、执行、结果返回构成主线；成果存储是独立分支，不成为所有任务的无条件前置。
- 图中的合成节点不表达实际设备、固定节点数量或已验收的平台映射。
- 关系源、SVG 与 PNG 的节点文字、方向和标签应一致；文本解析、渲染与实际运行验收分别报告。
- 身份／并行、存储／归档和平台边界的变更应同时检查接口、状态、失败与恢复语义；编译检查不能替代依赖安装或原生后端验证。
- 产品设计不记录具体部署凭据、主机映射或原始运维输出；此类配置和证据使用独立的私有部署记录。

本轮从首节点认证部署登记与 P0／P1 开始，沿第 7 节先完成独立认证、当前主体项目授权和必要隔离，再完成五名额、持久队列及项目互斥；其他平台与 NAS 各自推进，复用已有适用证据。只有对应阶段的实际证据通过后，才能更新能力、平台支持和部署完成状态。本次仅细化既有设计，不改变运行配置、不切换服务、不将评审中的方案计为部署完成。
