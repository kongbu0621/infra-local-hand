## 已确认并修订的两项问题

| ID | 原设计的具体反例 | 最小修订 | 验收映射 |
| --- | --- | --- | --- |
| RC-01 | 业务 J 已取消，独立核对 R1 启动后回执丢失；query/cancel 只收 J 的 id/digest，无法明确重取或停止 R1。用旧业务事件序号判同一快照，还可能把旧观察冒充当前事实 | reconcile 使用客户端稳定 reconcile_id，先持久后启动；status/cancel 明确寻址业务或准确核对轮次；同 id 重取，新 id 才申请新观察；保持单父作业互斥与 UNKNOWN 屏障；保留七工具 | R03/R04/R09 → A03/A05/A07 → V03/V04/V08/V10 |
| RC-02 | 创建意图前须核对固定输入，而该核对又必须交给先登记意图的 helper；不区分意图类型会形成循环前置，或把慢 I/O 放回启动围栏 | 受限辅助观察意图与业务执行意图分阶段登记；准入预检不许可业务执行，预检合格且绑定仍有效才登记业务意图；分别呈现辅助已执行与业务是否启动 | R01/R04 → A03/A05 → V01/V04 |

RC-01 同时明确缺失记录的含义：健康账本 NOT_FOUND 不证明仍在传输的请求以后不会受理；
不能因此换 id 重投。对未找到目标的 cancel，本版不新增取消 tombstone，只返回取消未受理；
没有持久取消屏障绝不报告取消完成。I/O 不明单独返回 IO_UNCERTAIN。

RC-02 复用既有阶段、helper、账本、预算和围栏；没有新增可执行 kind 或外部工具。
预检事实仍受不可变输入与稳定挂载边界保护，事后摘要或旧观察不能替代使用时的绑定保证。
