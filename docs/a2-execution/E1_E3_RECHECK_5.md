## 多路复核与失败分类

本轮分别检查 broker/状态/资源、runner/固定 Ledger、认证/MCP/维护 CLI、证据/下载、契约/策略/Plugin，并交叉复核业务结果交界、wheel、目录身份与容量锁。真实 SQLite、文件、子进程、密码学及 loopback HTTP/SDK 与合成 manager、issuer、回调分别记账。

- **准确基线反例。** 预算探针在准确旧源码上分别观察到 remaining 为 0 和 -1 时启动真实合成子进程并写出标记。业务报告测试确实执行子进程，再在结果目录 fsync 边界注入失败；systemd/cgroup 与主机准入仍为模拟。目录替换和 wheel 轮换使用真实文件操作、受控时序注入；这些都不是断电实验。
- **新增可信标志的反向合同。** Broker 首次 red 的另一项失败验证新标志下的外来/缺失执行身份拒绝，不能另算实际旧 Manager 可达的基线漏洞。循环测试在首个断言失败处停止时，只记录实际到达的子例；最终通过可覆盖其余子例，但不能倒推它们均已独立复现旧故障。
- **同一容量缺陷的并发遗漏。** 初版串行余量修复通过后，独立双 Store 探针仍实际得到两次 SEALED、两次登记、四个目录，超过两项上限；在准确旧 main 上也复现，确认属于既有问题。最终独立探针观察首个持锁、第二个立即 RESOURCE_BUSY，释放首个后 SEALED 且只登记一次；随后调用 LIMIT_EXCEEDED，保留两项目录与源内容。最终探针使用有限事件协调，不沿用修复后无法满足的双 writer 屏障。
- **修复期根锁绑定反例。** 首次加锁补丁在持锁 FD 与命名根解绑后可能先登记，再在 context 退出时报 CONFLICT。该失败属于修复期间，不写成旧 main 原有加锁行为。最终在写入前与登记前检查根绑定，回归覆盖 snapshot 和 publication 两个时点；原 red 实际只到达第一个时点。
- **探针构造错误。** wheel 初始 red 命令的启动子例因合成 profile 缺少必要字段，未到目标边界；保留失败，修正 fixture 后在未改产品源码上单独确认启动核验缺陷。认证异常 claims 首次由 PyJWT encoder 提前拒绝，也未进入 verifier；后续使用成熟签名库构造合法签名的异常载荷，原失败脚本仍保留。
