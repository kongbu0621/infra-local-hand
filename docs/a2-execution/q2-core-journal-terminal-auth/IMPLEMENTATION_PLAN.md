## T1 最小修改

准确 A 及 Owner B 之后，先独立 bookkeeping-only C，再实现 D。未批准前不改变旧 argv 或重开预检。
仅在原两个维护实现文件中接通显式终端认证模式、普通终端资格检查、私有 manifest 绑定和
writer 专用的控制终端继承；不泛化修改所有 Command 的进程组行为。
复用原 payload、八检查点、时钟、输入 pins、guest 协议、备份与增长流程。
scope/A/C/source manifest 记录新批准链，原两个 A 三文档保留历史准确字节。

本地 Codex 已有的现场记录须先取得、审阅并按既有发布授权推送；不伪造 `7fd8a1e` 的完整 SHA 或内容。
本提案可在独立文档分支审阅，集成时保留本地记录及 R→A→B→C→D，不重写或 squash 批准链。
如现场记录与截图存在会改变方案的矛盾，先报告具体差异，不据截图宣称已完成独立现场核验。

## T2 针对变化验证，冻结一次

使用现有九文件窄测试和正常相关 CI；仅扩充真正受影响的终端/认证测试：

- 无 fd 0 TTY、后台进程、session/设备替换、两次 CLI 换终端在相应边界拒绝；前台 PGID 合法变化不误拒绝。
- 独立 PTY 合成环境证明 writer 保留控制终端，stdin 仍 DEVNULL，stdout/stderr 保持独立且有界。
  使用固定模拟认证程序和虚构输入；禁止真实口令进入测试、日志或 AI。
- 实际 argv 无 `-n/-S/-A`，没有 sudo-v、askpass、重复调用或可选 shell；其它命令 session 行为未改变。
- 同一终端两 CLI 的原窗口/nonce/输入绑定与全部八检查点保持；缓存存在与不存在两种情况均不跳过验证。
- 认证失败、超期后模拟认证、TTY 消失、人工中断、sudo 内部 PTY/管道情况分别保留准确退出/UNKNOWN。
  root entry 到期后不得调用 scanner；关机后认证失败不得重启、清理或重试。
- 原生 pidfd 与合成 qcow2/ext4、writer 不可读/drift、输入保护、容量、源码大小和每步失败停止继续通过。

合成 PTY 测试不等于真实账号已获 sudo 权限；CI 不触碰原主机或原 VM。
准确最终 D、完整 argv/payload、原输入、终端模式和全部相关 CI 通过后才安排本人在场的 T3。
不为验证认证另启一次现场 root observer；第一条实际观察才检验当前策略和本人认证是否可用。
实现后交付普通用户在真实终端运行的准确入口及原路径，不要求用户编辑代码、改 sudoers 或把密码发给 AI。

## T3 一次新窗口，条件沿用原维护

取得本地失败记录、完成 T2，Owner 在本机终端就绪。新窗口之前只核对已有输入和终端准备，
不发 sudo 请求，不开启 SSH，不创建 marker。其后仅一次新 900s/780s 双时钟窗口。

以原 session 运行固定预检，由本人只在真实 sudo 提示出现时直接认证；每次可能再次提示，
不可假设仅第一次需要密码。预检与 execute 使用同一准确 D、终端、输入和窗口 binding。
需要人工交接的私有摘要按原协议返回，等待时间计入原窗口，不另造窗口或新持久 marker。

仅全部原门通过后执行原单次 J3：正常关机、离线完整备份、一次镜像增长、一次原配置启动、
被动等待、一次 ext4 增长、内容与普通可用容量验证。累计次数与预算全部沿用原 A。
失败立即停止后续步骤，报告首个具体原因、已发生修改、进程退出与现场计数；不自动重试或回滚。
不增加第三条 SSH、不补采、不清理历史证据、不进入 H01/Q4/H11。完成维护后才据真实结果接回核心验收准备。

完成定义是准确候选及其现场 receipt；模拟成功或 CI 成功均不能替代现场扩容结果。
不保证密码认证后所有后续条件必过。旧失败、所有 UNKNOWN、未完成用量观测及 production E3 限制保持。
