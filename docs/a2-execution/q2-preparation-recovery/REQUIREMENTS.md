## 问题与变更边界

原 `LH-Q2-FIXTURE-PREP-v1` 已获批准。实际执行已成功创建计划中的主组；随后 `useradd` 因把 `CREATE_MAIL_SPOOL` 作为不支持的配置项传入而退出 3。原命令退出与双流 EOF 完整。只读报告确认用户名和 UID 均不存在，后续计划目录尚不存在；准确实例身份与原始记录留在私有证据中。

原准备结果保持 `INCOMPLETE`。原准备期限已经过去，而且实现没有在准备意图中持久保存完整 issued/deadline，不能直接重新计时并声称原准备成功。原架构允许恢复的前提是证明原意图、原对象、未交付步骤且无额外预算；此次需要一个**明确新增、最多 300 秒的恢复管理时窗**，因此单列变更，由 Owner 决定。

该新增时窗是本提案唯一的期限扩展。账户/组数量、七个 project、所有路径、配额、安装候选、operation 身份和持久容量仍受原计划及原批准范围约束；时间预算不能从未使用的容量上界推导。

## 精确范围与排除项

保留同一 preparation ID。新的 recovery attempt ID 仅用于区分追加证据和一次恢复交付，不能成为新的 preparation、quota allocation、broker operation 或运行重试身份。

允许保留并证明本 preparation 已创建的唯一主组，新增尚不存在的计划账户，完成原批准但未交付的对象，并进行尚未发生的那一次原监督运行。原失败记录与恢复结果同时可查；`RESOURCES_RECOVERED` 或 `PREPARED` 只证明对应实际新结果，不抹去原 `INCOMPLETE`。

禁止删除/改名/重建原主组、重新分配账户或 project、回收或退款、清空账本、重放 quota 设置/manager 启动/运行交付、替换原安装候选、修改旧 Q1 对象、包或内核升级、挂载及 fstab 变更。GX10、现役 S1、真实 NAS、Q3 接纳和 E4–E6 均不在范围内。

## 预算和完成定义

恢复调用使用以下四个独立且嵌套的上限：

| 层次 | 最大时长 | 边界 |
| --- | --- | --- |
| 外部管理与捕获 | 300 秒 | 包含 guest 交付、退出、两路 EOF 和封存 |
| guest 恢复 service | 270 秒 | 包含恢复准备、装配及首次正常运行；停止上限另为 3 秒 |
| 恢复鉴证、准备与装配 | 140 秒 | 从 guest 恢复入口开始，首次鉴证读取前固定绝对期限；不按步骤刷新 |
| 尚未发行的原 Q2 owner | 120 秒 | 保持既有 envelope，且启动时须留足停止和 EOF 费用 |

CPU 总上限 300 秒，内存最多 512 MiB，PID 最多 64，外层 stdout/stderr 合计最多 2 MiB；单命令继续受原计划较小上限约束，最长 30 秒。上述限制与原计划适用限制同时执行，不以新上限扩大原对象费用。原计划 450 秒准备上限留作历史，新 140 秒是待批准的独立恢复上限，不能冒称恢复了旧期限。

所有持久写入、暂存与日志计入原计划的 installation/state/journal/capture 分类及原批准上界，包含已有失败和本次新增记录。不能因另有 recovery ID 重获一份容量。恢复和尚未发生的运行共同受本次 300 秒外层时窗约束；剩余时间不足以完整容纳原运行、停止、EOF 和封存时，不启动运行。

完成交付包括准确新恢复计划、来源、原失败关联、现场鉴证、实际恢复回执、原正常首次运行及完整外层退出证据。模型测试和真实宿主结果分别报告。通过本提案不自动通过 Q2 故障实验、Q3 或生产验收。
