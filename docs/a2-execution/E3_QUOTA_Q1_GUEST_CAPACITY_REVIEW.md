## 上界如何覆盖峰值

在已交付 fixture 的受信管理约束下，实验期间使用这四块固定盘，没有授权的扩容、换盘
或外部持久写根。交付脚本的目标写根均在 guest 内；查询、writer、边界检查和后续复核
保持原 mount/root 绑定。检查现有交付脚本未发现扩盘操作；原创建与当前容量一致。
这依赖既有“受信管理员、稳定代次、无其他 writer”的实验模型，不声称可以排除未披露的
管理员扩容后缩容或其他越过该管理约束的操作。若出现该类事实，本复核须重新打开。

因此，对该固定 guest 范围内任一时刻，实际持久分配的峰值受上述原虚拟容量总量约束。
系统盘按整盘计入，避免漏算 root 分区外的 boot、日志或临时构建文件；同一系统盘上的
安装和控制目录不再各加一次可用预算。数据盘上的 payload、日志、原件和同时存在的
封存副本均落在同一硬边界内，FS 元数据也不能突破其所在块设备的原大小。

这是保守的容量上界证明，**不是精确历史峰值测量**。不把当前占用当成历史峰值，
也不把逻辑文件大小当成已分配块数。内存/tmpfs 使用仍由已交付 guest 和单元内存预算
负责，不能作为额外持久空间或未计费的封存目的地。

四个唯一配额域的硬限额合计为 `64 + 64 + 4 + 64 = 196 MiB`，即 205520896 bytes，
小于原 2 GiB 数据盘，也小于复核报告的该 FS 总量 2040373248 bytes。
原 UNKNOWN 的 64 MiB 保持全额计入，没有按当前空目录退还。
这 196 MiB 已包含在数据盘上界内，不能再与整盘容量相加而重复计费。

## 不外推的范围及下一阶段

guest 虚拟容量不等于宿主 qcow2/backing/metadata 的物理空间预留；本记录没有证明宿主
总物理预算、NAS、外部 ZIP 副本或生产吞吐。它们不包含在上述限定 guest 的容量结论中。
后续若新增外部保留、扩盘或 host 部署，必须在对应新工作开始前另行固定其容量和来源，
不得引用这份 27.25 GiB 上界替代。Q2 管理协议仍需逐请求的明确原分配和容量记账，
不能给普通作业使用整个 VM 的容量作为预算。

Q2 可以按已批准范围继续接口、绑定、管理预算和恢复实现；Q2 尚未完成。
