# 部署恢复：实现与验证边界

本记录对应[重构方案](DEPLOYMENT_RECOVERY_REFACTOR.md)与[使用说明](DEPLOYMENT_RECOVERY_USAGE.md)，
记录 2026-10-25 的源码实现和隔离验证。它不是现役服务迁移完成记录，也不把模型测试、
文件实测、systemd 实测合并成一个“全部验收通过”的结论。

## 已实现的协议

本次继续完成原准备与成果兼容的生产调用链，而非只增加维护屏障的独立测试：

- 计划器枚举原准备；协调器在排空后保存原绑定与原成果读取基线。目标配置隐藏原任务、原准备漂移、
  未闭合派发以及成果变化均阻止切换或释放；回退和交接复用原基线。
- 跨部署 READY 的明确兼容决定进入原操作记录，再发布到维护屏障，绑定完整目标加载身份。
  不兼容准备不自动执行，也不阻止其他新准入；原准备接续仍走鉴权入口。
- 守卫 MCP 与停止态一次性读取器实际读回原状态、清单和全部成果分块；比较原任务与完整字节，
  首次增加 MCP 不因路由组件名称不同误报结果变化。只读打开不初始化证据目录、不重写原写入版本。
- 原控制器通道已丢失时，固定准备适配器可沿只读原账本返回，原账本锁仍拒绝存活写入者。
  跨开机维护责任通过原控制器、cgroup 和排队作业观察闭合；原未知业务结果不变。
- 排空后重新读取责任数量，正向与补偿均可在该次接续内继续；临时读取器清理所有资源并保留主错误。
- 下发前检查完成、补偿和释放的逻辑记录预算；普通等待与未闭合观察不使用恢复事件保留额。

源码验证已覆盖真实 SQLite、原策略、三个封存文件的完整读回、未使用 READY 的临时读取锁释放、
成果损坏、任务身份冲突、记录预算和补偿接续。root 私有 Unix 验收入口及真正主机重启观察需分别取证；
本段不将模拟旧开机、模型管理器或普通用户测试计为这两项通过。

[`c398f7f`](https://github.com/kongbu0621/infra-local-hand/commit/c398f7f1466b437dd8d3e86976cbbb4bbe59a0a8)
补全了以下实际入口和约束：

  拒绝新操作时不再遗留孤立记录；准备后的响应丢失沿 `PREPARING` 继续，不因自己的暂存物重做基线判定。
- 共享重载保留原 loaded_snapshot，将已核对的混合磁盘树作为动作前置条件，后继显式 reload；网关
  保留有限的中间规格用于准确恢复。两者的管理器/Engine 故障验证仍按下表区分模型与真实平台。

  2xx 在响应头阶段判为安全失败。安全修复先持久关门、限制网关，再排空业务；不安全原目标不能重新开放。
- 宿主 MCP 可经守卫绑定受保护 Unix HTTP socket，供独立 namespace 的 nginx 通过同路径目录挂载访问。
  真实 socket 验证覆盖存活监听拒绝、停止后准确回收及退出不删除替代对象。
- 公网检查失败返回非零；部署、准入、公网、客户端、恢复、诊断分别携带证据身份。外部未知与历史版本
  成功不会变成本地部署成功的附属结论。

服务动作限于画像中的普通 systemd 服务、精确启用链接、共享 reload 及有限依赖关系。

不拉取镜像，不创建额外网络或卷，不执行项目级 down。镜像、daemon、原 Compose、既有网络、
只读 bind 和启动证明都需明确绑定。此实现事实与真实 Docker 生命周期验收是两回事。

## 隔离 systemd 组合实测

可重复入口为 [deployment_recovery_systemd_smoke.py](../tests/e3_host/deployment_recovery_systemd_smoke.py)：

```bash
python3 tests/e3_host/deployment_recovery_systemd_smoke.py --run-isolated-user-service
```

它要求可用的普通用户 systemd 管理器及支持普通持久文件句柄的本地文件系统。
脚本只创建随机临时单元、私有配置、监听 socket、维护状态和部署数据库；不接入默认测试发现，
不启用自启动，不调用共享 `daemon-reload`，不操作现役单元或 Docker。临时单元设有限运行时限，
测试结束执行停止及单元文件清理，配置目录随后清理。

本轮在 systemd 255.4 的普通用户管理器上完整运行退出 0，实际验证：

1. 原进程读取旧配置，通过真正的 `startup.authorize` 后建立私有监听；运行证明由 socket 对端
   UID/PID、进程启动身份、InvocationID、实际配置及载荷摘要核对。
2. 真实 `Coordinator`、SQLite `Store`、`MaintenanceGate`、文件适配器及 `SystemdAdapter`
   执行停止、配置替换、候选守卫启动、本地核验、稳定选择及开放，得到 `COMMITTED` 且释放完成。
3. 重复同一 `apply`，实际 InvocationID 与维护序号不变。
4. 对已提交操作调用 `rollback`，创建固定回退后继，使用保留的原配置备份恢复原字节，实际启动旧配置，
   回退后继得到 `COMMITTED` 且释放完成。它是新回退部署的提交，不把原提交改写成 `ROLLED_BACK`。
5. 再次调用原 `rollback` 返回同一后继，InvocationID 与维护序号不变；旧、新、恢复旧共三个不同
   InvocationID，最终维护状态为 `OPEN`，原配置字节完全恢复。随机临时服务已停止并清理。

该脚本的固定 `Environment` 是测试夹具，所有上述效果来自真实文件、进程及管理器；它不是
生产 `ConcreteEnvironment`、现役 MCP/网关或管理员安装投影已运行的证据。未发生共享 reload，
因此不能用此次成功确认共享管理器重载画像完整。

独立作业传输实测还覆盖了丢失 `job_accepted`/`JobRemoved` 记录：监督子进程在实际接收后退出，
恢复通过原发送者消失、目标状态及无剩余目标作业核对，未重复下发。该项使用随机临时服务，
与上述普通服务组合验证分开记录。测试脚本最初的准备目录/字段错误发生在部署动作前；
一次清理连接重复订阅的错误也已保留为测试过程错误，最终脚本使用独立清理连接完整退出成功。
