# 归档文件系统身份修复（2026-10-17）

## 触发与需求

PR #48 部署后，沿原真实归档的 Artifact/Version 读取时，旧消费者返回数据库身份冲突。
保留记录显示设备号发生变化，但 inode、数据库完整摘要及其他原文件仍与原留档一致。
首次失败没有写入；不能将这次误拒报告成 Ledger 数据损坏，也不能删除身份文件绕过检查。

长期归档需要在同一持久文件系统的设备号重新分配后仍可读取。原有数据库替换拒绝、原请求
幂等核对、已确认提交回执和回滚检查仍须保留。这里修复本地归档消费者，未增加 MCP 工具、
临时测试入口、NAS 操作或任务执行能力。

## 实现边界

- 新库使用 v3 消费者格式，保存文件系统 ID 和 inode；任务预约中保留原身份，避免改写原请求。
- 旧库不会因读取失败自动接受当前文件。`bind-filesystem` 是明确的本地维护命令，需要可信历史
  数据库摘要、原 inode、完整 Ledger 验证和现存提交回执核对，仅追加一份不可变绑定。
- 缺失、替换、损坏、错误摘要、含 sidecar、回执矛盾或绑定损坏均拒绝；维护命令不会初始化数据库
  或执行 create/append。新旧数据库文件、原身份和回执均保留。
- 文件系统 ID 必须在所用文件系统的重挂载之间保持稳定。接口本身不保证所有文件系统具有这一
  性质；不承诺克隆文件系统、删除后 inode 重用或绕过归档锁的并发写入。用户操作见
  [使用说明](USAGE.md#filesystem-identity-after-device-renumbering)。旧消费者不能打开新 v3 库。

## 验证

修复安装源码为 `14c823d347b1183842c9ae81316c9a77a9572cd8`。源码和独立 wheel 安装分别通过
同一组 86 项归档/证据检查，两组覆盖重合，不相加为独立场景数量。新增检查覆盖设备号变化后
精确读取与 resume、文件系统变化拒绝、缺失绑定拒绝、v1/v2 补绑定和重复调用、错误摘要、
数据库替换、三类 sidecar、确认操作丢失后的拒绝重放，以及真实独立 CLI 进程。

消费环境使用已验证 Ledger wheel 的 17 个产品模块，逐字节等同于 Ledger PR #14 合并提交
`58b08fa9cb188c48feec45592a0f775c7178fd7a` 的模块。两包安装后的 82 个 Python 产品文件与
所选 wheel 一致；原留档数据库 SHA-256 作为本次维护信任输入，没有以当前未知文件自算摘要
代替历史证明。

真实原库核验结果：

- 15 个原文件和数据库字节保持一致，仅新增文件系统绑定记录。
- 按原 Artifact/Version ID 读回五个归档文件，19 个封存成员全部核对一致。
- 沿原 producer/operation 执行 resume，返回原版本、原时间戳和 `reused=true`。
- Ledger 仍为 1 个 Artifact、1 个 Version、5 个 Blob、2 条幂等记录；数据库写入为 0。
- 从升级后的真实 MCP 连接取回的 ZIP、清单、封印与归档中的原字节相同，没有重放源任务。

原错误、原文件清单、可信旧摘要、调用返回、安装包与校验记录保持私有留档。修复核验使用独立
归档安装；管理/API 服务继续运行 PR #48 合并版本 `f526ca2`。未因验证修改 NAS 或其安装。
受控测试模拟身份字段变化，没有为测试重启宿主或重新挂载真实磁盘。

## PR #49 复核：维护核验与回执边界

本轮在合成归档中先复现两处缺口，再修复；上述真实原库并未用作故障注入对象：

- 把 `create.json` 错放为 append 请求时，原维护代码按文件内容选择另一份回执，可能漏查
  create 回执并仍返回成功。append 回执缺失时，还会额外生成该回执。现在先检查请求类型与
  固定回执位置一致，维护调用使用仅核验模式，既不执行缺失操作，也不生成回执。
- append 回执保留、create 回执丢失时，原维护代码未核对隐含的 create 历史；删除 create
  幂等记录后，Ledger 结构验证仍可通过，维护也会误报成功。现在沿原 create 请求检查该记录，
  缺失即拒绝，与原 resume 的判定一致；记录完整但缺少回执时，绑定保留这一事实，不补写回执。

新增回归覆盖上述拒绝、只有 create 的中断归档、单份回执缺失，以及绑定目录发布前/后中断的
重试。失败检查核对原文件字节与文件集合不变；发布中断的 staging 原件保留，重试不执行
Ledger 操作。源码及修复提交 `864537a499dc83f6f432508992c41de83867ea49` 的独立 wheel 安装
各通过同一组 90 项归档/证据检查，包含原有 86 项；这两组覆盖重合。两个变更 Python 文件
编译通过，独立安装的 82 个 Python 产品文件与所选两份 wheel 一致。

修复安装还复核了上述真实旧库：已有绑定返回 `reused=true`，没有新增文件；含此前绑定在内
的 16 个文件及数据库完整摘要全部保持一致。指定版本读回的五文件、19 个封存成员与原留档
一致，resume 仍返回原版本及原时间戳。未重跑源任务，管理/API 服务和 NAS 未改动。

## 2026-10-18 复核：请求归属必须与原任务一致

继续复核发现，上一轮的请求类型检查仍不足以证明任务归属。合成的两个归档分别有有效 Ledger
记录和回执；把另一任务的同类型请求及回执放进当前任务目录，维护核验仍会成功。在原 create
回执与幂等记录缺失的情况下，换入另一任务的 create 请求也能掩盖原操作缺失。三个场景均先
复现旧代码错误接受，再验证修复后的拒绝；真实归档没有参与故障注入。

创建请求与维护核验现共用从原任务映射派生的模板：核对请求格式、类型、幂等作用域和键，
以及 Artifact/Version 身份、内容根与来源关系，再检查原回执和 Ledger 记录。模板保留 v1
按 token 划分、v2 按任务划分的既有语义；不以待检查请求自己声称的身份选择其他任务的记录。
维护路径依旧不执行 Ledger 操作，不生成缺失回执，不把部分归档补做成完成状态。

新增两项回归覆盖跨任务替换、已确认 create 被另一任务掩盖、映射格式/身份损坏及修复后的
同请求重试；原 v1 请求兼容检查增加重复绑定验证。源码同组归档/证据检查共 92 项通过；
两个变更 Python 文件编译通过。另与上一轮独立安装比较，v1/v2 请求及载荷字节完全一致。

修复提交 `9b78640a290fb5ad35c8e48a6f5333e8f8f2e702` 的独立 wheel 安装通过同组 92 项检查，
与源码覆盖重合；82 个已安装产品 Python 文件与两份选定 wheel 一致。该安装再次沿真实
原归档完成已有绑定核验、指定版本读取和原请求 resume：16 个文件及数据库字节不变，无新增
文件；仍返回原版本、原时间戳，五文件与 19 个封存成员一致。没有重放源任务，服务和 NAS
保持原状态。
